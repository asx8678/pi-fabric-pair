# Changelog

## Unreleased

- **A crashed worker tells you how to recover.** When the worker process dies while Main runs, Pair holds the task (detected within a second in a live SIGKILL test) but only showed "Worker stdout ended before confirmed exit", and the status view suggested `/pair resume`, which refuses until the held generation is stopped. The notice and the status view now say `/pair stop`, then `/pair resume`; after the stop, the status view suggests `/pair resume` instead of `/pair start`. Checked live: stop then resume continued the same worker conversation, the worker checked the workspace per Pair's recovery instruction, redid the step and reported.
- **Main gets Pair's tool fields up front.** With Fabric's code mode, Main sees Pair's tool names but not their parameters. It guessed arguments (`pair_inspect` without `workerId`, `pair_decide` approval without `feedback`) or spent a round trip on `tools.describe` before dispatch, inspect and decide. At a 140k-token context on grok each extra round trip cost about $0.07. Main's guide now lists the fields of `pair_dispatch`, `pair_inspect`, `pair_decide` and `pair_cancel`, and says that approval needs a summary `pair_inspect` (without `file`) of each report. Checked live with Kimi K3 and GLM 5.3 as Main on a rename with callers and one revision: no `tools.describe` calls and no Pair-tool argument errors (before: 2–3 describes and one refused approval per review).
- **Known limitation: Pi 0.87.1 does not run Pair's cache-warming decisions.** Pi's idle warmer stops before its first refresh once a session holds a custom message (Pair's guide, task-state and report messages) while an extension handles `agent_before_settle`, which Pair, Fabric and Fovea all do. Every settle rebuilds those messages as new objects, and Pi's warmer compares them by identity. The docs no longer say both caches are kept warm. A value comparison in a scratch copy of Pi made warming work end to end: the worker refreshed at 219 s, and its first request after a 270-second review read 99% from cache instead of 2%.
- **A Fabric compaction no longer kills the worker.** When Fabric's compactor summarises the whole live context it writes the compaction with an empty `firstKeptEntryId`, which Pi reads as "keep no earlier entry". Pair's session-history check accepted only an entry id, so the next work prompt after such a compaction failed ("Broken compaction reference"): the worker was killed and the task held. The check now accepts the empty reference as Pi does. Checked live with a small context window: the worker compacted mid-step, Pair's task-state packet restored the original context, and step 2 used a word that appeared only in that context.
- **A budget pause, `/pair pause` or `/pair cancel` no longer kills a busy worker.** Pair revoked the worker's authority and only aborted its run afterwards, so a tool call the worker started in between counted as foreign activity: Pair faulted the worker and killed it ("Worker ran tool fabric_exec outside a current activation"), and the task was held for recovery instead of paused. These paths now start the abort at revocation, as report acceptance already did, so that tool call is the tail of the abort. Checked live with a 100-token output budget: the task paused, the worker stayed ready, and you get one notice.
- **A crashed Main keeps its repository.** The repository lock belongs to the Main process, so after a crash any other Pair session could take it and dispatch a second worker over the crashed session's unresolved task and its partial changes. The resumed task's checkpoint would then include the other worker's edits. Pair now takes over a dead session's lock only once that session's saved state has no unresolved task in the repository. Otherwise the dispatch is refused with the session to reopen (`pi --session <id>`, then `/pair resume` or cancel) and the state folder to delete to abandon it. Checked live: SIGKILL of Main mid-task, a second session refused, the original session resumed and completed, then another session could take the repository.
- **Leaving Main mid-task asks first.** `/new`, `/resume` or a fork closes the session's Pair controller, which stops the worker and interrupts its task. Pair now uses Pi's cancellable `session_before_switch`/`session_before_fork` hooks to confirm while a worker task is running (TUI only).
- **Less worker noise on Main's screen.** Only the worker's warnings and errors are forwarded; info-level notices from its extensions (Fabric's entropy runs appeared three times in a 40-second task) are left out.
- **`/pair doctor` warns when `.pi/fabric/` is not ignored.** The worker's Fabric writes runtime state such as `.pi/fabric/mcp-cache.json` into the workspace. Found in a live end-to-end run: without a `.gitignore` entry it shows up as a changed file in every checkpoint.
- **The worker no longer re-reads its whole work order every turn.** Each worker turn's task-state packet included the original objective and context (up to 24,000 characters), and in final-only plans every continuation and revision work order repeated the full plan and context. One real worker session carried 18 copies (107k characters) with no compaction. The original context now travels once, in the first work order, and the packet restores it only after compaction, as documented. A final-only revision with a 20k-character context shrinks from about 20.6k to 650 characters.
- **Report turns keep Main's cache and Fabric's guidance.** A report that woke an idle Main started its turn with a custom message (`sendMessage` with `triggerTurn`), which in Pi 0.87.1 skips `before_agent_start`. So that turn ran without Fabric's system-prompt section (and without Fovea's sync or Pair's guide): the prompt prefix differed from user turns, and both missed the cache. In real sessions, 33% of report-started turns were smaller than the previous request, the next user turn grew by a median 3.5k tokens, and 44% of those user turns were full cache misses (18% for other user turns). An idle delivery now appends the report and starts the turn with a fixed Pair prompt through Pi's normal prompt path (`sendUserMessage`). A busy Main still gets the report as a follow-up in its running turn. Pair's own wake prompt is not counted as your input. Checked in a live Pi process: the old path sent no `before_agent_start` system-prompt section; the new path does.
- **Both roles' prompt caches are kept warm while one waits on the other.** With Pi's `"cacheWarming": "idle"`, Pair answers Pi's `cache_warming_decision`: for Main while the worker works or its finished report waits to be delivered (the report starts Main's next turn), and for the worker while its checkpoint, question or blocker waits for Main. There it applies Pi's savings rule ($0.05) with that next request treated as certain; it never returns `stop` and never changes settings. A report made through `fabric_exec` ends the worker's run on an aborted request with no usage, so Pi priced a zero-token prompt and never warmed (60 of the last 68 real reports); when Pi's `missCost` is 0, Pair prices the last measured prompt with the model's rates and tiers. Codex models are never warmed: Pi sends that API no output cap, and the ChatGPT backend rejects `max_output_tokens`, `prompt_cache_options` and `prompt_cache_retention` for `gpt-6-astra`. This covers every model: Pi warms only models with a `promptCache` lifetime (built in: Anthropic only), so each role gives the model about to run a 240-second lifetime when Pi knows none, never changing a known one (set a per-model value under `modelOverrides` in `models.json`). `/pair doctor` says when a role uses a Codex model; Main's guide and `/pair doctor` say when Fabric's `cache.hold` is unsupported on this Pi. Checked against Pi 0.87.1's own `CacheWarmer`: a 120k-token Main on Kimi K3 or GLM 5.3 gets refreshes with Pair and none without; in a live Pi process, a lifetime set on `ctx.model` at turn start reaches Pi's warmer.
- **Fewer wasted round trips on tool arguments.** 12% of recent worker `pair_report` calls and 9% of Main `pair_inspect` calls failed Fabric's type check, each costing a full extra model request. The worker guide now lists `pair_report`'s exact fields, and `pair_inspect` accepts the optional `taskId` Main kept passing (it must be the current task's).
- **A cache-warm refresh no longer faults the worker.** Pi records each refresh as a `usage` entry in the worker session. One landing during the history check before a work prompt made the check fail ("RPC history has a broken leaf"), which stopped the worker and held the task. The check now runs again, at most twice, when Pi announced an appended entry during it; any other difference still fails.
- **More Fabric effects are caught in the worker.** `agents.subscribe` (a lasting subscription that can start later turns), `cache.hold` (a paid lease) and `components.apply` (a Fabric configuration change) now count as detached effects alongside `agents.spawn`, `agents.create`, `agents.import` and `jev.spawn`, each with its own description. A worker `fabric_exec` whose code calls any of them directly is now blocked before it runs, so no effect happens and the worker keeps going; the check ignores strings and comments, so an edit payload or grep pattern that mentions them passes. A computed ref still reaches the existing result check, which shuts the worker down.
- **Fabric's `schema.commit` no longer slips past Pair's write rules.** It writes files with no `tool_call`. While Main supervises a task with `mainReadOnlyDuringTasks`, a Main program that calls it is blocked before it runs, and a commit reached through a computed ref warns you that the checkpoint may include Main's changes. In the worker, a commit that lands after `pair_report` closed the lease (possible only in parallel with the report, which aborts the rest of its program) is a detached effect.

- **Fabric agents and actors started from the worker are caught.** Fabric's provider actions raise no `tool_call`, so the worker gate never saw `agents.*`, and a durable `agents.spawn`/`agents.create` launches a detached Fabric resident host before Fabric's depth check. That host could outlive the worker, Pair's stop and Main. The worker now reads Fabric's `tool_result` proxy: a successful `agents.spawn`, `agents.create`, `agents.import` or `jev.spawn` fails that call, records a detached effect and shuts the worker down, like a background shell. The controller refuses to freeze a checkpoint while a resident host recorded under the worker's private mesh (`fabric/mesh/residency/*/owner.json`) is alive, and `/pair stop` warns when one survives. Pair never signals that PID, because the worker can write the file. The `agents.`/`actors.` pattern in the worker gate, which could never match, is removed.
- **Cache guidance follows the loaded Fabric.** Main was told to use `cache.status()`/`cache.hold()`, which only exist from Fabric 0.97.0. Main's guide now names them only when the loaded Fabric is 0.97.0 or newer, says warming is unavailable on an older Fabric, and says the version is unknown when it cannot be read; `/pair doctor` notes an older Fabric. Docs state the version requirement.
- **Fabric-first fixes (Phase 1 of `docs/FABRIC-FIRST-PLAN.md`).** Pair loads inert inside Fabric child agents and actors, which Fabric marks with `PI_FABRIC_PARENT_RUN`: no Main controller of its own, no worker role from inherited variables. The Prewalk requirement now asks only that Prewalk cannot auto-arm (`prewalk.alwaysRearm` not `true`), so Main keeps manual `/fabric prewalk`; probes recorded earlier keep the old reading. `/pair transcript` reads the tail of the worker's saved session instead of asking the worker for its whole context, so viewing it can no longer fault a running worker, and it works while the worker is stopped. An oversized `agent_end` or `turn_end` line is delivered by type without the payload Pair never reads; any other oversized line still faults. Reports and `pair_yield` summaries tell Main to run `fovea_impact` on the changed files (summaries now carry `repositoryRoot`), and the reference documents `capture.risks` for Pair's tools.
- **Cache warming delegated to Fabric.** Fabric 0.97.0 ships a `cache` provider (`cache.status`, `cache.hold`, `cache.release`, component `cache.lease`) built on the same optional native `acquireCacheWarming("idle")` capability Pair used, with stricter fencing (model, thinking, system prompt, tool set) and one shared native lease across owners. Pair's own lease code is removed: `src/warming.js`, the `cacheWarming` setting (a legacy key is accepted and ignored), the `cacheWarming` authority field publication, the worker telemetry `warming` field and the `Warming` status rows. Main's guide now points at `cache.status()`/`cache.hold()` inside `fabric_exec`. Pair still shows measured cache reads and never simulates warming.
- **Offline test suite restored.** `npm test` runs `tests/*.test.mjs` again (111 passing). The fake Pi hosts now honour `get_entries { since }` like Pi, which the incremental history verification requires, and the framing test follows the current rule that a stray non-JSON stdout line is a diagnostic, not a fault. Tests written against the previous widget UI and delivery model are kept but not run: whole files under `tests/stale/`, single tests with `{ skip: 'stale: …' }`; `tests/README.md` explains how to re-derive them.
- **Reports never interrupt Main and never displace your prompt.** A finalized report is durable pending work, delivered only at a safe boundary: at the settlement boundary of a normally completed Main run with no queued user message (Main reviews after finishing its own work), from the `agent_settled` handler (Pi defers it in order with prompts submitted during settlement), or as a new turn when Main is idle, with the idle check repeated in the same tick as the send. Reports are no longer attached to your prompt. If your prompt still collides with an idle-wake report turn, Pair takes it over, stops the report turn and sends your message next as a normal prompt. Aborted or failed Main runs no longer wake Main with a report.
- **Delivery receipts are observation-based.** A sent report counts as offered only once Main's session holds it; while Main is busy the wait continues instead of timing out into a duplicate, and a report already in Main's session is never sent again (including after a crash). `/pair yield` no longer reports a false failure. `deliveries.jsonl` logs claims, deferrals, observations and retries.
- **Recovery after a Main crash.** The worker's PID is recorded at spawn. On restart Pair proves the previous worker exited and releases it automatically; otherwise the new `/pair reconcile` proves the exit, offers to stop that process group, and as a last resort asks you to confirm. Pair only ever signals a validated child PID's process group (never PID 0/1, itself or its parent).
- **Long-lived worker sessions.** Retained session history is verified incrementally (prefix hash plus appended entries) instead of re-reading and re-transferring the whole file on every activation, removing the 16 MiB ceiling. The work prompt's acknowledgement now waits through Pi's preflight (including a compaction) instead of failing after 30 s.
- **Workspace changes during review no longer kill the worker.** Drift during a configured check fails that check (`VERIFICATION_SOURCE_DRIFT`) and the report still reaches Main; drift while freezing the checkpoint is retried, then the task is held with the worker kept.
- **Stray worker activity.** A turn another extension starts in the worker is aborted instead of killing the worker, and a tool call the Pair gate blocked is harmless (Pi announces tool starts before the gate runs). New `runtime.excludeExtensions` leaves inherited extensions out of the worker; `/pair doctor` lists inherited extensions that start turns on their own.
- **Default task revision limit raised from 3 to 20.** With the per-step limit (3) now enforced, a task-wide limit of 3 refused legitimate fixes late in multi-step plans. Explicitly configured values are unchanged.
- **Limits are enforced or removed.** `activeStepTimeoutMs`, `maxRevisionsPerStep`, `maxReportBytes` and `maxAutomaticReportRepairs` are now enforced. `every-step` enforces `supervision.maxStepFiles` (default 5): a larger checkpoint cannot be approved. `maxQueuedTasks`, `maxQueuedReviews` and `maxAutomaticRecoveryAttempts` are deprecated (accepted, then dropped).
- **One writer per repository.** A repository lock stops a second Pair session from dispatching into a repository while a task there is unresolved.
- **Main stays available.** `pair_dispatch` and `pair_decide` return once the assignment or decision is durable; the worker starts in the background and a failure is reported to you and to Main.
- **Faster evidence.** Captures re-hash only files whose inode, size, mtime or ctime changed; manifests reference their snapshot instead of embedding it; resolved notices, old request IDs and evidence of older tasks are archived or collected.
- Smaller fixes: the Main guide is a one-time context message when no Pair tool is active (no per-run system-prompt change); approval requires a summary `pair_inspect` (a single-file read acknowledges but does not count); a crash-safe, PID-reuse-aware ownership lock; directory fsync after state writes; key-order-independent request and decision hashes; `cancel` via `pair_decide` revokes only after validation; an explicit `activating` task status; stray non-JSON stdout from an extension no longer kills the worker; Pi peer range `>=0.87.1 <0.88.0` with a startup warning on other versions; the large PNG is no longer packaged.

- **Fixed: the workflow stopped after the worker reported.** Finalized reports only waited in the inbox, and nothing woke Main unless it had called `pair_yield` before its turn ended, so Main never reviewed the work. New setting `autoDeliverReports` (default `true`) sends each finalized report to Main as a follow-up message that starts a turn. It only fires when Main is idle (otherwise at Main's `agent_settled`), only for reports no `pair_yield`/boundary delivery has already offered, and at most `limits.maxReportsPerTask` (default 40) times per task, so a report is never delivered twice and question/answer loops stay bounded. Main's guide now tells it to inspect every report, approve only correct work, and `revise` with concrete fixes otherwise, which sends the work back to the worker until it is approved, cancelled or the revision limit is reached. Set `autoDeliverReports: false` for the previous explicit-yield behaviour.

- **Fixed: Pair's UI said reports never wake Main.** The waiting-report line told Main to call `pair_yield`, `/pair status` said there was no automatic idle wakeup, and `/pair yield` said nothing wakes Main. With `autoDeliverReports` on (the default) each report starts a Main turn once Main is idle, and every delivery, manual ones included, starts a Main turn. The text now follows the setting and says so.
- **New status line.** Pair now shows one line in Pi's footer (its own `setStatus` key): each worker's state and flow arrow, the current step, and, only while it runs, tool, speed and context pressure; then cost, reports waiting for Main and last cache reads (`cache M 99% W 100%`). A worker that is not running names the command that continues it. The multi-line widget is gone: in `minimal` mode one line above the editor shows the active plan (approved/total bar and current step), and the new `compact` mode shows the status line only. `off` still hides everything. The widget is mounted once and redrawn only when the plan changes, instead of being rebuilt every 2 s. No elapsed time or turn count is shown.
- `/pair` stays open after each action and redraws from fresh state, closing once a delivery hands the turn to Main; restart, reload and doctor moved under **More…**. Stopping a worker asks first when it would interrupt a running task. `/pair status` now leads with each worker's state, task and plan, groups sessions, warming and accounting under Details, and has a shorter legend. Settings show On/Off and describe each indicator mode. Costs use one format everywhere (`$0.013`, `$1.23`, `<$0.001`). Step titles and tool names are stripped of control sequences before inline display.
- Main, the worker and the fabric-pair skill now call Pair's tools directly inside `fabric_exec` (`await extensions.pair_status({})`, `await extensions.pair_report({...})`, the same in Python) instead of searching the catalog and using `tools.call`, which cost extra calls and often extra model turns; `tools.describe` is only a fallback after an argument error. The skill no longer says reports never wake Main. `gateTool`'s comment now states that Fabric's own providers (`agents.*`, actors, `rlm`) never reach it and that `agents.maxDepth = 0` is what stops Fabric spawning in the worker.
- **Redesigned Pair's panels.** Status, inbox, report, diff, transcript, delivery and doctor views open in a centered bordered panel (at most 110 columns) with the title in the top edge and position and keys in the bottom edge, so the chat behind no longer shows through and nothing is drawn over the footer. Wrapped lines continue under their indent, bullet or value instead of at the left edge. `/pair status` is grouped into Worker, Task, Activity, Reports, Main and Details with aligned rows, shows `not chosen yet` instead of `/` for a missing worker model (and points to `/pair settings`), shows tokens as `272k`, hides speed for a worker that is not running, and has a shorter legend. The inbox shows one card per report and explains itself when empty. `/pair doctor` leads with pass/fail checks (extensions, the worker's Fabric profile, migrations, enabled, worker models) before the raw data. The `/pair` dashboard and settings use a bordered menu with sections, aligned values in color, a hint for the selected row and Escape to go back; the worker model picker uses the same frame. Worker-written text in reports is indented and never styled.
- **Worker effort now follows the chosen model.** Pair hardcoded the effort list as `off`–`xhigh`, so models that support `max` (such as gpt-6-luna) could not select it, and models without `off` (such as gpt-6-astra) still offered it. Settings now read the worker model's registry entry and apply Pi's own rule (a model without reasoning supports only `off`; levels mapped to `null` are unsupported; `xhigh` and `max` only when mapped), show only the supported levels with what each is sent to the provider as, flag a saved effort the model does not support, and move the effort to the nearest supported level when you pick a different model, as Pi does. `max` is accepted in saved settings. If an unsupported effort still reaches startup, the error now names the effort Pi used instead.
- **Pair's views now look like Pi's own dialogs.** The rounded boxes and floating overlays are gone: status, inbox, report, diff, transcript, delivery, doctor, the dashboard, settings and the pickers open inline in the editor area with Pi's plain rules, accent title and key hints (`keyHint`, so remapped keys show as remapped). Menu rows follow Pi's `/settings` list: the `→` cursor, aligned labels, muted values and the selected row's description below; option pickers mark the current choice with `✓` like Pi's thinking picker, and headings use Pi's markdown heading color.
- **Quicker worker setup.** The `/pair` dashboard shows a Set up section while Pair is off or no worker model is chosen (turn it on, choose the model), and the worker's Model and Effort rows with their values, editable in place through the same save path as `/pair settings`. Settings list the worker's Model, Effort and Review policy first. With no model chosen, the status line says `/pair to set up`.
- **Fixed: opening Pi outside a Git repository reported a worker error.** Autostart started the worker in Main's folder (for example your home directory), which fails because Pair records review evidence with Git. Pair now checks each worker workspace, skips autostart there with one notice, shows `not a Git repo` in the status line, dashboard, `/pair status` and doctor, and the start error explains how to fix it (open Pi in a Git project or set the worker workspace in /pair settings → Advanced). The requirement itself is unchanged.
- **The status line says what is happening.** Instead of symbols (`M● → W◉`), it now states the stage and who has the work: `Worker working on step 2/5`, `Worker revising step 2/5` after Main asked for changes, `Checkpoint 2/5 ready for review · Main is reviewing`, `Question for Main · Main is busy; delivered when idle`, `Task done · worker ready`, `Worker stopped · not a Git repo`, `Worker not set up`, `Pair off`. It follows with the current step's title and the worker's live activity in words (`editing src/controller.js`, `running npm`, `running Fabric code`), then speed, context pressure, cost and cache reads. The worker now reports what its current tool acts on: a workspace-relative path for file tools and only the program name for shell commands, never their arguments. The dashboard header uses the same words.

Completed steps must stay unchanged as its prefix; the task's `planRevision` advances (counted once against the revision limit), old-revision reports are rejected, and `work-order.json` is rewritten so post-compaction scope restoration keeps working. The worker receives the revised plan in the decision message.

- A worker can resubmit its identical locked-in report: the tool gate now lets `pair_report` through after the report latch, so the DUR-01 republish path is reachable. Other tools stay blocked.

- Reworked the Pair TUI. `/pair` now builds its menu from the current state: waiting reports come first (review, diff, deliver to Main), and each worker only offers the lifecycle actions that apply (no Start while running, Resume only when held, Cancel asks for a reason). Added read-only `/pair report` (a report card separating Pair-captured files and checks from the worker's claims) and `/pair diff` (colored checkpoint diff with real file names and added-file contents); neither marks a report inspected, so Main must still `pair_inspect` before approving. `/pair inbox` and `/pair yield` show readable lists instead of JSON. The scroll view sizes to the terminal, honours keybindings, wraps wide characters correctly and adds `g`/`G`, `/` search with `n`/`N`, and `[`/`]` file jumps. The widget names what a waiting worker waits on (`← W◐ question`), shows the plan of the active worker (labelled when there are several), and the waiting line is shorter.

- Fixed `answer`/`revise` decisions made after the workspace drifted from the report's checkpoint. They were recorded first and then failed the continuation guard, which left the report resolved, the task interrupted and the worker contained. Every continuation now checks the live workspace before recording, so a stale decision is rejected and the report stays open; restoring the reported state makes it decidable again. The `pair_dispatch` result and README now say reports wait in the inbox for `pair_yield` rather than arriving automatically.
- The worker's `before_agent_start` and `turn_start` hooks now abort when authority or latch loading fails. Pi only logs a throwing handler, so an invalid authority file previously let the turn run as an unleased paid request.
- An unchanged retained latch (and an unproven inbox candidate) no longer rewrites and fsyncs `state.json` and re-renders the widget on every 350 ms scan; only an adopted report or a newly recorded stale entry persists.
- RPC framing no longer discards buffered data on a fault. A partially received frame survives a fault raised elsewhere, frames after an invalid line in the same chunk are still handled (so containment's control ACKs arrive), and an oversized frame is skipped to the next newline. Incomplete frames are accumulated as parts, so a large frame arriving in many chunks is no longer rescanned per chunk. Added offline framing, worker turn-gate, stale-decision and scan-persistence regressions.

- Added `/pair restart [worker]` and `/pair reload`, also available from the dashboard. Restart rereads settings and replaces only the worker after confirmed exit, retaining its conversation, progress and evidence while Main stays open. Interrupted work requires explicit resume; model changes stay staged until tasks finish or are cancelled. Reload validates saved settings without launching workers, and invalid files preserve the last valid configuration. Added command and child-process regressions for failures, retained history and lifecycle races.

- Fixed retained-worker startup when native model selection records a default thinking level before Pair applies the configured effort. Each setter's observed history suffix is validated separately; exact final selection, append-only history, branch checks and aggregate suffix bounds remain enforced. Cancelling an already-exited worker no longer attempts a dead-process abort RPC, and containment retains the original fault alongside recovery guidance. Added isolated startup and cancellation regressions; no automatic inference retry or conversation reset.

- Removed visible timing from the widget and `/pair status`: worker rows no longer show a numeric activity-age badge, elapsed task duration or turn counts, and the `Cache read (last)` percentages no longer carry an "ago" timer. Internal timestamps, startedAt/turn counters, liveness thresholds (2m pulse stop, 5m stale), one-shot stale notifications with their diagnostic durations, heartbeat behavior and raw machine-readable telemetry are unchanged; a silent worker is still marked with a plain error-colored `stale` badge/row, and a stale task still reports plain STALE guidance without an elapsed number.
- Unstaged ordinary file↔directory replacements no longer block checkpoints. A tracked file whose path became a directory is captured as a missing path — its removed before-image stays inspectable from immutable evidence — while Git still enumerates the new nonignored descendants; a former directory replaced by a regular file records its removed descendants as missing beside the new file. True submodules and embedded Git repositories still fail explicitly: gitlinks are identified by index metadata (mode 160000) rather than directory shape alone; untracked nested-repository directory names are rejected, and so is a tracked path whose replacement directory carries nested-repository metadata (a `.git` directory, gitfile or symlink marker, never followed or recursed into). Symlink-ancestor escape rejection, leaf-symlink capture, special-file rejection and evidence bounds are unchanged, and NUL-delimited index parsing handles spaces, tabs, newlines and multiple merge stages.
- Added an average streaming-throughput label to the worker indicator row (`W avg 42.3 tok/s`; explicit `avg — tok/s` while unavailable) and `/pair status`. The value is a weighted aggregate — summed provider-reported output tokens over summed measured `message_start`→`message_end` seconds per worker session/model — so 100 tokens in 1s plus 100 tokens in 3s averages 50 tok/s, not 66.7. Pi emits `message_start` only once the provider response begins streaming, so pre-response request/prefill latency is excluded and tool execution or idle gaps are never counted; zero-output, unmatched, and nonpositive/nonfinite samples are dropped without touching a good aggregate. The aggregate resets on session/model boundaries, survives compaction (pending timing clears, the completed average remains) and stays visible in waiting/ready/paused states.
